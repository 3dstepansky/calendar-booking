## 2. Фронт работ для полной готовности (Roadmap to Production)
Хотя ядро системы и интерфейс гостя работают исправно, для того чтобы продукт можно было передать конечным пользователям (Организаторам), необходимо выполнить следующий объем работ:

### 🟧 Шаг 1: Создание Панели управления (Dashboard) для Организатора
В данный момент у организатора нет интерфейса. Необходимо разработать закрытую зону во фронтенде (или отдельного Telegram бота):
1. **Экран авторизации:** Кнопка "Войти через Google" (интеграция с существующим эндпоинтом `/api/v1/auth/login`).
2. **Экран настроек профиля:** Указание своего часового пояса (Timezone) и контактных данных.
3. **Настройка расписания:** Интерфейс (матрица времени), где организатор выбирает дни недели и рабочие часы. Привязка к таблице `WorkingHours`.

### 🟧 Шаг 2: Управление бронированиями
- Разработка интерфейса (список/таблица) во фронтенде, где организатор может видеть все предстоящие встречи.
- Реализация кнопки "Отменить встречу" с автоматическим удалением события из Google Календаря и отправкой уведомления гостю.

### 🟧 Шаг 3: Деплой и инфраструктура
- **Production Server:** Перенос Docker-контейнеров на рабочий виртуальный сервер (VPS) с открытыми портами (Выполнено частично, требуется SSL).
- **Reverse Proxy & SSL:** Настройка Nginx/Traefik на новом сервере для обеспечения HTTPS-соединения (обязательное требование Google OAuth для callback-ссылок в production, а также для решения проблемы Mixed Content при запросах с GitHub Pages).
- **Rate Limiting:** Защита API от спама бронирований.

## 3. Методология обеспечения качества и тестирования (QA & Testing)
Для того чтобы продукт можно было назвать полностью исправным и готовым к реализации, необходимо внедрить процесс тестирования. Ниже приведена пошаговая декомпозиция:

### Шаг 1: Разрешение инфраструктурных блокировок
На данный момент сквозное тестирование (E2E) заблокировано ошибкой `Mixed Content` (фронтенд HTTPS пытается достучаться до бэкенда HTTP).
*   **Решение:** Настроить доменное имя для VPS и выпустить бесплатный SSL-сертификат (Let's Encrypt), чтобы API было доступно по адресу `https://api.yourdomain.com`.
*   **Альтернатива для тестов:** Временно запускать фронтенд локально (`localhost`), где правила Mixed Content не применяются так строго.

### Шаг 2: Симуляция пользовательских данных (Seeding)
Поскольку графического интерфейса Организатора еще нет, базу данных необходимо подготовить к тестам вручную:
1.  Выполнить логин через эндпоинт `/api/v1/auth/login` для получения реального Google `refresh_token`.
2.  Выполнить SQL-запрос `INSERT INTO working_hours` для создания расписания (например, ПН-ПТ, 09:00 - 18:00).

### Шаг 3: Сквозное ручное тестирование (End-to-End)
Проверка реального пользовательского сценария:
1.  Открыть Telegram Mini App или сайт как Гость.
2.  Выбрать свободный слот на завтрашний день.
3.  Заполнить форму и нажать "Подтвердить".
4.  **Валидация:** Открыть Google Календарь Организатора и убедиться, что событие физически создано, а гость получил Telegram-уведомление (если бот подключен).

### Шаг 4: Покрытие критической логики автотестами (Unit Tests)
Написать тесты для класса `SlotEngine`, так как это ядро системы:
*   Тест: Правильно ли вычитается занятое время (`freebusy` Google) из рабочего времени.
*   Тест: Корректно ли обрабатываются часовые пояса гостя и организатора (чтобы 15:00 в Москве не превратилось в 15:00 в Лондоне).
*   Тест: Попытка двойного бронирования (Race Condition) — отправка двух одновременных запросов на один и тот же слот.
